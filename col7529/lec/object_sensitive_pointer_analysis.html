Object-Sensitive Pointer Analysis

We have seen that a call-context-sensitive points-to analysis is more precise than a call-context-insensitive analysis. We now introduce a new idea, by first showing the limitations of call contexts.

Recap: The Running Example with Call Contexts

Recall the following program. There is a class Memory with a field m; D1 and D2 are two derived classes of a common base class that declares a virtual function f, and D1::f and D2::f are its two implementations. The main program sets m to objects of the two different derived classes, then calls getM, and then calls the virtual function f: 
class Memory {
  Base *m;
  void setM(Base *sm) { this->m = sm; }
  Base *getM()        { return this->m; }
};

main() {
LM1: m1 = new Memory;
LM2: m2 = new Memory;
LD1: m1->setM(new D1);
LD2: m2->setM(new D2);
LR1: r1 = m1->getM();
LR2: r2 = m2->getM();
     r1->f();
     r2->f();
}
A call-context-sensitive analysis with a call-context depth of one is able to precisely identify that r1->f() calls D1::f and r2->f() calls D2::f. Knowing this statically, the compiler can generate faster code at the dispatch of these functions (e.g., a direct call instead of a virtual dispatch).

This works because the call contexts at the two call sites of setM are different (LD1 and LD2). The pointer variables in setM (this and sm) are versioned based on the call context, e.g., smLD1 and smLD2. As a result, the corresponding updates are also versioned: through the LD1 version, the field m of the first Memory object is updated, and through the LD2 version, the field m of the second Memory object is updated. This is why we get a precise answer.

Limitation of Call Contexts: A Helper Function

Let us change the example a little. Instead of updating m directly, setM calls a helper function h, and h updates m: 
class Memory {
  Base *m;
  void setM(Base *sm) {
LH: this->h(sm);
  }
  void h(Base *hm)    { this->m = hm; }
  Base *getM()        { return this->m; }
};
We have increased the call depth on this path (from setM to the actual update of m) from one to two. With a call-context depth of one, the analysis now becomes imprecise.
  • If we increase the call-context depth to two, the analysis becomes precise again. But increasing the call-context depth has a multiplicative effect on the running time of the analysis (e.g., it can go from n to n2), and so this is usually not done.
  • Moreover, no matter what call-context depth we use, we can always construct a program on which the analysis gives imprecise results, by making the call depth (call-stack depth) of the program greater than the call-context depth of the analysis.

Analysis with Call-Context Depth One

We label the call site of h as LH, and version all the variables based on their call sites:
  • Variables of setM (this, sm) are versioned using its two call sites, LD1 and LD2.
  • Variables of getM (this) are versioned using its two call sites, LR1 and LR2.
  • Variables of h (this, hm) are versioned using its call sites; but there is only one call site, LH. Even though setM may be called through two different call sites, h is called through only one call site. So there is only one version, thisLH, of the this pointer in h.
This single version is the source of the precision problem. Both Memory objects become potential pointees of thisLH, and so the analysis concludes that the field of each Memory object may point to the other one's pointee.

Below, an abstract object is named by its call context followed by its allocation site; e.g., L0M1 is the object allocated at site LM1 in context 0 (the context of the top-level main function).

Without h (the original, precise solution): thisLR1 of getM points to L0M1, and thisLR2 points to L0M2; similarly, thisLD1 and thisLD2 of setM point to the respective objects. As a result, r1 may point only to a D1 object, and r2 may point only to a D2 object, and the virtual function calls are resolved precisely.

With h: the fixed-point computation proceeds as follows.

  1. h has only one version of its this pointer, thisLH (the one context in which it is called), but it is reached on two call paths. So thisLH may point to either L0M1 or L0M2. This is the first place where something points to both Memory objects.
  2. Similarly, there is only one version of hm, hmLH, which may point to either L0D1 or L0D2.
  3. Transferring across this->m = hm in h: because thisLH may point to either L0M1 or L0M2, and hmLH may point to either L0D1 or L0D2, it appears that L0M1 may point (through field m) to L0D2, and that L0M2 may point to L0D1. The imprecision accumulates. 
    L0M1 --m--> L0D1, L0D2
L0M2 --m--> L0D1, L0D2
  4. Finally, at the getM calls, this->m may point to either a D1 object or a D2 object. So r10 may point to either L0D1 or L0D2 (an extra edge r10 → L0D2), and likewise r20 gets an extra edge r20 → L0D1.
This is an imprecise solution: the compiler can no longer statically resolve the calls to the virtual function f.

Object Contexts

The problem is that, on the call from setM to the helper h, the call context changes from LD1 to LH (or, on the other call path, from LD2 to LH). One approach to avoid this is to increase the call-context depth, but that is too expensive.

Another idea: instead of the call context, use some other context that makes more sense, or is likely to give better results. We can group the contexts in any way we like; usually, contexts are engineered carefully so that they give the most precision for the least running time of the analysis.

The idea is to use an object context. If there is a transition from one function to another function within the same object, then we assume that the (object) context does not change. In our example, the call context changes because the last call site changes, but the this object under which we are executing has not changed.

  • We track the this object under which the function body is being analyzed; if the this object remains the same, we keep that context.
  • This is only possible for object-oriented languages.
  • Rationale: the program's behaviour is likely to be similar within a single object, and different across different objects.
  • This likely works better than call contexts, at least for object-oriented languages, because the pattern of calling helper functions (within the same object) is very common in such languages.
Just like the call context, the object context is a heuristic that may or may not work. There are examples where object contexts work worse than call contexts, and examples (like the one above) where object contexts work better. But in general, for object-oriented languages, object contexts typically work better than call contexts.

Assigning Object Contexts: Abstract Objects as Contexts

Just as for call contexts, we need a finite number of statically identifiable contexts. For call contexts, we look at all the call sites (or, for depth two, all the call-site pairs that can potentially appear in the program).

But the number of runtime objects is unbounded: there can be an unbounded number of allocations of a particular class, and a member function may be invoked on each of those objects. So the same function may be called under an unbounded number of object contexts.

We already know how to deal with this: we use abstract objects as the object contexts. e.g., using the allocation-site abstraction, all objects allocated at an allocation site are grouped under the same abstract object, and that abstract object is used as the context under which a member function of that object is analyzed.

In our example, the allocation site LM1 acts both as an allocation site (an abstract object, i.e., a node in the points-to graph, as before) and as an object context for member function calls through that object:

  • m1 points to abstract object LM1, so for the call m1->setM(...), setM is analyzed in the object context LM1. If m1 could point to multiple abstract objects, we would analyze setM in each of those abstract-object contexts.
  • For m2->setM(...), setM is analyzed in the context LM2.
  • Similarly, getM is analyzed in contexts LM1 and LM2.
  • h is also analyzed in the same two contexts LM1 and LM2. On the transition from setM to h, we do not look at the call site; we look at the abstract object of the this pointer at the call (LM1 or LM2), and h is analyzed under that same context.
Compare with the call contexts: LD1/LD2 for setM, LH for h, and LR1/LR2 for getM. Because we changed the definition of a context, the object contexts are completely different. The big improvement is that we now have two contexts for h, and in each, it is precisely known whether this refers to the first or the second Memory object.

Allocation Sites under Object Contexts

main does not execute in any object, so we use the context 0 for main. The allocations m1 = new Memory and m2 = new Memory give: 
m10 --> LM1
m20 --> LM2
There is a slight difference from the call-context analysis, where we named the object L0M1 (remembering the context 0 in which the allocation was performed). We assume an object-context depth of one. We need a finite number of object contexts, so we cannot keep track of all the object contexts that we came through. The allocation itself represents a new context, so the old context (0) is forgotten and the abstract object is just LM1. i.e., a call context grows across a call, whereas an object context grows across an allocation.

Running the Object-Sensitive Analysis on the Example

  • m1 = new Memory (LM1), m2 = new Memory (LM2): m10 → LM1, m20 → LM2.
  • m1->setM(new D1): new D1 creates the abstract object LD1. m10 points to LM1, so setM is analyzed in context LM1:
    • argument: smLM1 → LD1.
    • this pointer: during a member-function dispatch, the formal this is also updated, to point to the receiving object: thissetMLM1 → LM1.
    Similarly, m2->setM(new D2) gives smLM2 → LD2 and thissetMLM2 → LM2.
  • this->h(sm) in setM: h is called under the same this object, so its context is whatever the receiving object is, i.e., LM1 (whatever thissetMLM1 may point to). This is where precision improves:
    • argument: hmLM1 ⊇ smLM1, so hmLM1 → LD1.
    • this pointer: thishLM1 ⊇ thissetMLM1, so thishLM1 → LM1.
    The same happens for the LM2 context: hmLM2 → LD2 and thishLM2 → LM2. If the receiver could point to multiple abstract objects, each of them would be a context, and we would perform these transfers for each of those contexts independently.
  • this->m = hm in h: draw an edge from whatever this may point to, to whatever hm may point to (labeled m in a field-sensitive analysis): 
    LM1 --m--> LD1
LM2 --m--> LD2
  • r1 = m1->getM(): thisgetMLM1 → LM1, and dereferencing this->m follows the m edge, which leads only to LD1. So r10 → LD1. Similarly, thisgetMLM2 → LM2 and r20 → LD2.
The final solution: 
m10 --> LM1 --m--> LD1
m20 --> LM2 --m--> LD2
r10 --> LD1
r20 --> LD2
This is a precise solution: r1->f() can be resolved to D1::f, and r2->f() to D2::f. It is as precise as the call-context-sensitive solution (depth one) for the program without the helper function h.

Moreover, there could be an arbitrary (unbounded) number of nested helper-function calls within a single class to its own member functions, and the object-sensitive analysis would still be precise, without having to increase the depth of the analysis. This illustrates why we expect an object-sensitive analysis to work better in practice, at least for object-oriented languages.

Formalizing the Transfer Functions

We now formalize the transfer functions for the object-sensitive analysis. The rules are very similar to those of the other points-to analyses we have seen (e.g., the call-context-sensitive analysis), and we use Andersen's analysis, i.e., we track the full points-to set of every abstract object. The only difference is in the way we track the context across function calls and across allocation statements.

Notation: pt(pC) denotes the points-to set of variable p in context C.

Allocation

In object context C, transferring across the allocation statement p := new ... at allocation site L: 
L ∈ pt(pC)
In the call-context-sensitive analysis, we would have said LC ∈ pt(pC). Here we use L, not LC: the context C is itself an allocation site, so LC would keep track of two allocation sites. With an object-context depth of one, we keep track of only a single allocation site, so we forget C and keep just L. (We generalize this to depth d below.)

Function Call Dispatch

Let o be an object of class O. In context C, consider the call: 
t := o.f(x)
where o is the receiving object, f is a member function, x is the actual argument, and t receives the return value (a call without a return value is a special case). Let the definition of f in class O be: 
O::f(a) = e
where a is the formal argument and e is the body of the function. Suppose that, in context C, o may point to abstract objects (allocation sites) K1 and K2, i.e., pt(oC) = {K1, K2}. (This generalizes to any number of abstract objects.)

Because o may point to K1 or K2, the callee is evaluated in both of these object contexts. For context K1, we apply the copy rule from the actual argument to the formal argument (as though aK1 := xC), and from the receiving object to the this pointer of the callee: 

pt(aK1)    ⊇ pt(xC)
pt(thisK1) ⊇ pt(oC)
and identically for context K2: 
pt(aK2)    ⊇ pt(xC)
pt(thisK2) ⊇ pt(oC)
Finally, the body e must be evaluated in both contexts, K1 and K2, i.e., all the transfers within e are performed both in context K1 and in context K2. Recall that the more contexts something is evaluated in, the more edges we add to the points-to graph (i.e., the less precision we have).

Function Return

Suppose that, inside the body e, the statement return b is evaluated in context K, where K ∈ pt(oC) (e.g., K1 or K2 above). Then the value of b in context K is used to update t in the caller's context C: 
pt(tC) ⊇ pt(bK)
i.e., on the return path, we apply the copy rule from the returned value b (in the callee's context) to the register t that holds the return value in the caller (in the caller's context). This is done for each callee context: if there are two callee contexts K1 and K2, then pt(tC) is updated using both pt(bK1) and pt(bK2).

Example: Appending to a Linked List

Consider a list class L with a field next, and a member function append(k) that appends k new nodes to the list (recursively: append one node, and then append k-1 nodes to it): 
class L {
  L *next;
  void append(int k) {
    if (k <= 0) return;
A2: n = new L;
    this->next = n;
C2: n->append(k-1);
  }
};

main() {
A1: l = new L;
C1: l->append(10);
}
The allocation sites are A1 (in main) and A2 (in append); the call sites are C1 (in main) and the recursive call C2. (We use . and -> interchangeably.) We write thisappend for the this variable of the append function, and use 0 as the context of main. We assume a field-insensitive analysis.
  • A1: l = new L (in context 0): l0 → A1.
  • C1: l->append(10): the receiving object l0 may point to A1, so append is evaluated in context A1, and its this points to whatever l0 points to: thisappendA1 → A1.
  • if (k <= 0) return: nothing to do (no pointers involved, and no value is returned).
  • A2: n = new L (in context A1): nA1 → A2.
  • this->next = n (in context A1): whatever thisappendA1 points to (A1) may now point to whatever nA1 points to (A2): A1 → A2.
  • C2: n->append(k-1) (in context A1): nA1 points to A2, so append is now evaluated in context A2: thisappendA2 → A2.
  • Evaluating the body of append again, in context A2:
    • A2: n = new L: nA2 → A2. Recall that we forget the context at an allocation site: with a depth-one object-sensitive analysis, the object is A2, not A2A2.
    • this->next = n: thisappendA2 points to A2, and nA2 points to A2, so we draw a cyclic edge A2 → A2.
    • C2: n->append(k-1): nA2 points to A2, so append is evaluated in context A2 again, which adds nothing new.
The fixed-point solution (you can check that it is a fixed point): 
l0 --> A1 --> A2 --+
                 ^      |
                 +------+

thisappendA1 --> A1          nA1 --> A2
thisappendA2 --> A2          nA2 --> A2
i.e., the variable l of main may point to an object allocated at A1; an object allocated at A1 may point to an object allocated at A2; and an object allocated at A2 may point to another object allocated at A2. The graph also seems to imply that an object allocated at A2 may point to itself, which is actually not true, but that is the imprecision we get in this points-to analysis.

Generalizing to Depth-d Object Sensitivity

So far, we have considered a depth-one object-sensitive analysis. It is easy to generalize this to a depth-d object-sensitive analysis, where a context is a string of up to d allocation sites. We define a bounded concatenation operator ⊕d that keeps only the d most recent allocation sites: 
l1 l2 ... ld  ⊕d  l(d+1)  =  l2 ... l(d+1)       (forget l1)
l1 ... le     ⊕d  l       =  l1 ... le l         (if e < d, keep all)
The allocation rule becomes: in context C, for p := new ... at allocation site L, 
C ⊕d L ∈ pt(pC)
With d = 1, we get exactly the rule we had before. With d = 2 or 3, we can tolerate longer strings. Everything else remains the same; the only thing that changes is what happens at an allocation site. e.g., with d = 2, an abstract object records that "this object was allocated at this allocation site, in the context of an object that was allocated at that allocation site".
