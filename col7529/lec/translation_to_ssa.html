Translation to Static Single Assignment (SSA) Form

Dominance Frontiers

The first step of the SSA translation algorithm is to identify the minimal set of convergence points at which trivial phi nodes need to be placed. This is done by computing the dominance frontiers of the nodes in the CFG.

Strict dominance: X strictly dominates Y (written X sdom Y) if X dominates Y and X ≠ Y.

  • Recall that the dominator relation is reflexive (every node dominates itself), but the strict dominance relation is not reflexive.
  • We write X !sdom Y to say that X does not strictly dominate Y; this relation is the complement of sdom. For example, B !sdom B always holds; and if B does not dominate C, then B !sdom C.

Dominance Frontier: The dominance frontier of a node X, written DomF(X), is the set of all nodes Y such that:

  • X does not strictly dominate Y (X !sdom Y), but
  • X dominates some predecessor P of Y.
DomF(X) = { Y | X !sdom Y  and  X dom P for some P in pred(Y) }

Intuition: if X dominates P and P-->Y is an edge, then there exists a path X-->...-->P-->Y where all the nodes from X to P are dominated by X (because every path from entry to P must go through X, and this includes the paths that go through the intermediate nodes). Y is the first node on this path that is not strictly dominated by X. In other words, look at all outgoing paths from X; on each path, the first node that X does not strictly dominate belongs to the dominance frontier of X. This is why the word frontier is used: it is the boundary at which X's (strict) dominance ends.

  • A node Z further down the path that is also not strictly dominated by X is not in DomF(X) if none of Z's predecessors are dominated by X.
  • Y may be dominated by X and yet be in DomF(X), if Y = X. e.g., if X is a loop header, then X may be in its own dominance frontier.

Example

Consider the following CFG (with edges entry-->A): 
A --> B, C
B --> D
C --> E
D --> B, F, G
E --> E, G
G --> F
Here, A dominates all nodes; B strictly dominates D; and C strictly dominates E. No other strict dominance relationships exist; e.g., F is not dominated by B because of the path A-->C-->E-->G-->F.
  • DomF(A) = {}: The only node not strictly dominated by A is A itself, but A's only predecessor is entry, which A does not dominate.
  • DomF(B) = {B, F, G}:
    • D is strictly dominated by B, so D is not in DomF(B).
    • F is not strictly dominated by B (path A-->C-->E-->G-->F), but F's predecessor D is dominated by B. Similarly for G.
    • B does not strictly dominate itself, but B dominates D, which is a predecessor of B (through the back edge D-->B). So B is in its own dominance frontier.
  • DomF(C) = {G}: C strictly dominates E, so E is not in the frontier. C does not strictly dominate G, but C dominates E, which is a predecessor of G.
  • DomF(D) = {B, F, G}: D does not strictly dominate any of its successors B, F, G; and D (which dominates itself) is a predecessor of each of them.
  • DomF(E) = {E, G}: G is not strictly dominated by E, but its predecessor E is dominated by E. Also, E is not strictly dominated by E, but its predecessor E (through the self-loop E-->E) is dominated by E. Here, X, Y, and P (in the definition) are all the same node E.

Computing Dominance Frontiers

Recap: dominator tree and immediate dominators. In the dominator tree, X dominates Y iff there is a path from X to Y in the tree. X immediately dominates Y (written X idom Y) if X sdom Y and there is no node C such that X sdom C and C sdom Y. Because the immediate dominator of a node is unique, we can treat idom as a function from nodes to nodes: idom(Y) is the parent of Y in the dominator tree. For the example above, the dominator tree is: 

A --> B, C, F, G
B --> D
C --> E
i.e., idom(B) = idom(C) = idom(F) = idom(G) = A, idom(D) = B, and idom(E) = C.

Some properties follow directly from the tree representation:

  • If X dom Y, then idom(X) dom Y (if there is a path from X to Y in the tree, there is also one from X's parent to Y).
  • If X sdom Y, then idom(X) sdom Y.
  • If X !dom Y (or X !sdom Y), then nothing can be said about whether idom(X) dominates (strictly dominates) Y. e.g., C does not dominate F but idom(C) = A does; whereas E does not dominate F and neither does idom(E) = C.

Naive algorithm: For each node X, perform a depth-first search on the CFG starting at X; on each path, stop at the first node that is not strictly dominated by X and add it to DomF(X). Each DFS takes linear time, and we perform one for each of the N nodes, so the running time is quadratic.

The naive algorithm recomputes each dominance frontier from scratch, even though DomF(X) is related to the dominance frontiers of X's children in the dominator tree. Note that if Y in DomF(X), Y may or may not be in DomF(idom(X)): e.g., F in DomF(B) but F not in DomF(A) (idom(B) = A); whereas F in DomF(D) and also F in DomF(B) (idom(D) = B). We define two relations to capture this.

DomFup: The nodes in DomF(X) that are "passed up" to DomF(idom(X)): 

DomF_up(X) = { Y in DomF(X) | Y in DomF(idom(X)) }
           = { Y in DomF(X) | idom(X) !sdom Y }
To see why the two definitions are equivalent: if Y in DomF(X), then X dominates some predecessor P of Y, so idom(X) also dominates P. Thus, if idom(X) !sdom Y, then Y in DomF(idom(X)) by definition. (The converse is similar.) The second form is easy to check: given DomF(X), keep only the nodes not strictly dominated by X's parent.
  • DomF_up(E) = {G}: DomF(E) = {E, G}; idom(E) = C strictly dominates E but not G.
  • DomF_up(D) = {B, F, G}: DomF(D) = {B, F, G}; idom(D) = B strictly dominates none of these (B dominates B, but does not strictly dominate it).

DomFlocal: The nodes in DomF(X) that are immediate successors of X in the CFG: 

DomF_local(X) = { Y in succ(X) | Y in DomF(X) }
              = { Y in succ(X) | X !sdom Y }
To see why: if Y is a successor of X and X !sdom Y, then X dominates a predecessor of Y (namely X itself, as dominance is reflexive), so Y in DomF(X).
  • DomF_local(B) = {}: B's only successor D is strictly dominated by B. (Recall DomF(B) = {B, F, G}, but none of these are immediate successors of B.)
  • DomF_local(D) = {B, F, G}: all three successors are not strictly dominated by D.
  • DomF_local(E) = {E, G}.

Theorem: 

DomF(X) = DomF_local(X)  ∪  ∪Z in children(X) DomF_up(Z)
where children(X) are the children of X in the dominator tree (and succ(X) in DomF_local refers to successors in the CFG). Intuitively, a node in X's dominance frontier is either an immediate successor of X that X does not strictly dominate, or is passed up from the dominance frontier of a node immediately dominated by X. In terms of the naive algorithm: the DFS from X either stops at the very first step (an immediate successor), or proceeds through a node strictly dominated by X, and so through one of X's children in the dominator tree.
  • DomF(A): DomF_local(A) = {} as both successors B and C are strictly dominated by A. A's children in the dominator tree are B, C, F, G; nothing in their dominance frontiers is passed up, because A strictly dominates every node other than itself. So DomF(A) = {}.
  • DomF(B): DomF_local(B) = {}; B's only child in the dominator tree is D, and DomF_up(D) = {B, F, G}. So DomF(B) = {B, F, G}.

Algorithm: Compute the dominance frontiers in a single bottom-up traversal of the dominator tree, so that the dominance frontiers of X's children are available when computing DomF(X): 

for each X in a bottom-up traversal of the dominator tree:
  DF(X) := {}
  for each Y in succ(X):              // DomF_local
    if idom(Y) ≠ X:
      DF(X) := DF(X) ∪ {Y}
  for each Z in children(X):          // DomF_up
    for each Y in DF(Z):
      if idom(Y) ≠ X:
        DF(X) := DF(X) ∪ {Y}
The check X !sdom Y reduces to idom(Y) ≠ X in both loops:
  • In the local loop, Y is a CFG successor of X, so if X strictly dominates Y, X must be Y's immediate dominator (any node strictly between X and Y in the dominator tree would have to lie on the edge X-->Y).
  • In the up loop, Y is in the dominance frontier of a child Z of X; if X strictly dominates Y, then (since Z does not strictly dominate Y) X must be Y's immediate dominator.
For example, DF(D) and DF(E) are computed first; then DF(B) reuses DF(D), DF(C) reuses DF(E), and DF(A) reuses the dominance frontiers of B, C, F, and G.

Running time:

  • The local loop examines each outgoing edge of each node exactly once: O(E) in total.
  • The up loop iterates over each child Z of each node X (N children in total, as this is a tree), and for each child, over DF(Z): O(∑X |DF(X)|) in total.
So the total running time is O(E + ∑X |DF(X)|). If dominance frontiers are small (e.g., constant-sized), this is linear in the size of the CFG. However, a single dominance frontier can be as large as N, so in the worst case this can still be quadratic. We characterize ∑X |DF(X)| in more detail later.

Placing Phi Nodes

The second step of the SSA translation is the placement of trivial phi nodes. Consider an assignment v := ... at node X, and let Y in DomF(X). Because Y is not strictly dominated by X, there must be another path to Y on which a different definition of v potentially reaches Y; this other definition is either another assignment to v, or the initial value of v at program entry. In either case, a phi node for v is needed at Y.

We stage the placement of phi nodes in two steps:

  1. Place a trivial phi node v := φ(v, v, ..., v) at Y, where the number of arguments is the number of incoming edges of Y. This is effectively a no-op instruction.
  2. Later, rename the variables so that the program is in SSA form.
Placing phi nodes only at the dominance frontiers satisfies the requirement for minimal SSA.

Some observations:

  • Transitivity: A phi node placed at Y is itself an assignment to v. So if Z in DomF(Y), then a phi node for v must also be placed at Z, and so on, until all phi nodes required by this transitive dominance-frontier relationship have been placed.
  • At most one phi node per variable per node: A phi node sits at the beginning of a basic block, and a block needs at most one phi node for each variable. e.g., if Z is in both DomF(X) and DomF(Y), only one phi node for v is placed at Z.
  • Per-variable: Phi nodes are placed separately and independently for each variable: 
    placePhis(P):
  for each variable v in P:
    P := placePhisForVar(P, v)
  return P

Algorithm: placePhisForVar(P, v) maintains three sets (represented as maps from nodes to booleans):

  • W (worklist): nodes whose DomF needs to be examined. It may shrink (when a node is picked) and grow (when a phi node is added).
  • consideredAlready: nodes that have ever been in the worklist. It only grows. A node's DomF needs to be examined at most once.
  • hasAlready: nodes that already have a phi node for v, to avoid placing duplicate phi nodes.
placePhisForVar(P, v):
  W := nodes with assignments to v
  consideredAlready := W
  hasAlready := {}
  while W ≠ {}:
    take X from W                         // W[X] := false
    for each Y in DomF(X):
      if Y not in hasAlready:
        place trivial phi node v := φ(v, ..., v) at Y
        hasAlready := hasAlready ∪ {Y}
        if Y not in consideredAlready:    // transitive step
          W := W ∪ {Y}
          consideredAlready := consideredAlready ∪ {Y}

Pruned SSA: Recall that pruned SSA additionally requires that a phi node for v is placed at Y only if v is live at Y (i.e., v may be used downstream). The algorithm above can be adapted to pruned SSA by additionally checking whether v is live at Y before placing the phi node. The liveness analysis can be run a priori, and only needs to be conservative; the more precise the liveness analysis, the more phi nodes may be eliminated.

Example

Consider a CFG with assignments to v at nodes X and W, and with the following dominance frontiers: 
DomF(X) = {Y}
DomF(Y) = {Z}
DomF(Z) = {U, X}
DomF(U) = {}
DomF(W) = {Z}
StepWconsideredAlreadyhasAlready
Initialize{X, W}{X, W}{}
Pick X; place phi at Y; add Y to worklist{Y, W}{X, W, Y}{Y}
Pick Y; place phi at Z; add Z to worklist{Z, W}{X, W, Y, Z}{Y, Z}
Pick Z; place phis at U and X; add U to worklist (X has been considered already){U, W}{X, W, Y, Z, U}{Y, Z, U, X}
Pick U; DomF(U) is empty{W}{X, W, Y, Z, U}{Y, Z, U, X}
Pick W; Z already has a phi node{}{X, W, Y, Z, U}{Y, Z, U, X}
The worklist is now empty, and the minimal set of phi nodes for v has been placed at Y, Z, U, and X. Note that X is not added to the worklist again when a phi node is placed at X: its dominance frontier has already been examined.

Running Time of Phi Placement

Define:
  • Aorig(X): the number of original assignments in basic block X; Aorig = ∑X Aorig(X).
  • Aφ(X): the number of assignments added due to phi nodes in X.
  • Afinal(X) = Aorig(X) + Aφ(X); Afinal = ∑X Afinal(X).
The number of phi nodes added to a single basic block can be as large as Aorig (e.g., all assignments in all other blocks may need a phi node in this block). So Aorig(X) ≤ Afinal(X) ≤ ~Aorig. Summing over all basic blocks (whose number is roughly proportional to Aorig): 
A_orig  ≤  A_final  ≤  ~A_orig2
i.e., the total number of final assignments can be quadratic in the number of original assignments.

Across all variables, the statement take X from W executes (at most) Afinal times, as nodes with phi nodes added by the algorithm are also added to the worklist. Each time, the inner loop executes |DomF(X)| times. So the total work is: 

∑X A_final(X) × |DomF(X)|  =  A_final × (weighted average DomF size)
where the average of |DomF(X)| is weighted by the number of assignments Afinal(X) in X.
  • Afinal is between linear and quadratic in the size of the original program.
  • The weighted average DomF size is between constant and linear (it can be as large as the number of basic blocks).
So the overall running time is between linear and cubic. We will characterize when this is linear (as is typical in practice) later.
